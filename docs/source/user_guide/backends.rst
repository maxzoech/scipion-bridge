Backends
========

.. currentmodule:: scipion_bridge

Protocols, shell commands, and proxies never talk to the operating system or
an execution engine directly. They ask for *services*, and a backend supplies
them through dependency injection (the ``dependency-injector`` package). The
same protocol code therefore runs unchanged in different environments.

.. contents:: On this page
   :local:
   :depth: 2

Services
--------

Each backend is a container that provides these services:

.. list-table::
   :header-rows: 1
   :widths: 25 75

   * - Service
     - Responsibility
   * - ``shell_exec``
     - Runs the commands generated by ``@shell_command``.
   * - ``temp_file_provider``
     - Creates and deletes temporary files for proxies.
   * - ``storage_provider``
     - Storage engine for the array types (Arrow).
   * - ``protocol_config_provider``
     - Serves parameter values to ``Field.value``.
   * - ``resource_provider``
     - Builds and caches ``Resource`` values.
   * - ``streaming_backend``
     - Compiles streaming graphs into runnable pipelines.

.. list-table::
   :header-rows: 1
   :widths: 20 40 40

   * - Backend
     - Use it for
     - Configure with
   * - Standalone
     - Scripts, notebooks, tests
     - ``scipion_bridge.backend.configure_default_env()``
   * - Ray
     - Parallel and distributed streaming protocols
     - ``RayPipelineRunner`` (configures itself)
   * - PyWorkflow
     - Running protocols inside Scipion 3
     - ``convert_protocol_to_scipion3_protocol``

Standalone
----------

The standalone container runs shell commands with ``subprocess``, creates
temporary files in the system temp directory, and caches resources per
process. Its streaming backend is Ray if Ray is installed.

.. code-block:: python

    from scipion_bridge.backend import configure_default_env

    container = configure_default_env()     # wires the scipion_bridge package

Wiring replaces the ``Provide[...]`` markers in the library with the
container's services. Pass ``modules=[...]`` to also wire your own modules.

Ray
---

The Ray backend compiles a streaming graph into Ray actors and tasks:

* sources, accumulators (``chunk``, ``collect``, ...), ``group_by`` demuxers
  and sinks become **actors**;
* every ``map`` call runs as a **Ray task**, scheduled by the compute resources
  declared with ``@B.resources``. Long-running protocols get a dedicated
  executor actor that holds their GPUs.

Stages run concurrently and push results downstream in order. Bounded queues
provide backpressure, so the driver slows down when the cluster cannot keep up.
Ray moves ``Set`` batches as Arrow buffers through its shared-memory object
store.

Running a protocol: ``RayPipelineRunner``
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

.. code-block:: python

    from pathlib import Path
    from scipion_bridge.backend.ray import RayPipelineRunner
    from scipion_bridge.backend.ray.sinks import TensorStoreSinkWriter

    protocol = FoundationModelInference()

    with RayPipelineRunner(
        protocol,
        parameters={"chunk_size": 512},
        sink=TensorStoreSinkWriter("latents.zarr"),
    ) as runner:
        runner.run(particles=Path("particles.star"))

``RayPipelineRunner(protocol, *, parameters=None, origin_types=None, sink=None, queue_size=2)``

``parameters``
   Values of the protocol's fields. Unknown names raise ``ValueError``, and so
   do missing required fields when the pipeline is compiled. Parameters without
   a value use their default. Use ``set_parameters`` to replace them before the
   first run.

``origin_types``
   The type each input is given as, by input name. The default is ``Path``.
   For every input, a resolver from this type to the declared input type is
   precomputed when the runner is created. It must contain a slice-aware step
   so that the input can be streamed in chunks (see
   :doc:`type_resolution`).

``sink``
   Where the protocol's output dictionaries go: a ``Sink``, a ``SinkWriter``, or
   a callback. **Without a sink, outputs are discarded.**

``queue_size``
   The number of items each stage buffers.

``run(**inputs)`` resolves every input in chunks and sends the chunks into the
pipeline, interleaving the inputs. When all inputs are exhausted, it flushes
the pipeline and prints the throughput and a table of per-stage statistics.
Use the runner as a context manager, or call ``close()``, to release the Ray
actors.

Environment variables
^^^^^^^^^^^^^^^^^^^^^

.. list-table::
   :header-rows: 1
   :widths: 35 65

   * - Variable
     - Effect
   * - ``SCIPION_CHUNK_SIZE``
     - The number of elements per input chunk. The default is estimated from
       the size of one element.
   * - ``SCIPION_TARGET_BYTE_SIZE``
     - The target size of an input chunk in bytes, used when the chunk size is
       estimated (default 32 MiB).
   * - ``SCIPION_STREAM_QUEUE_SIZE``
     - Overrides ``queue_size``.
   * - ``SCIPION_BRIDGE_CPUS``
     - *Set by the backend* inside stages that reserved CPU cores, for example
       to size thread pools.

Command line applications
^^^^^^^^^^^^^^^^^^^^^^^^^

``launch_as_terminal_application()`` builds an ``argparse`` parser from the
protocol's declarations and runs it. Inputs become path arguments. Field names
are converted to kebab case, so ``chunk_size`` becomes ``--chunk-size``. The
protocol's docstring becomes the program description.

.. code-block:: python

    # embed.py
    if __name__ == "__main__":
        RayPipelineRunner(FoundationModelInference()).launch_as_terminal_application()

.. code-block:: bash

    python embed.py --help
    python embed.py --particles particles.star --chunk-size 512 --model-type CRYO_IEF_SMALL

Running on a cluster
^^^^^^^^^^^^^^^^^^^^

``RayBackend`` starts a local Ray instance if none is running. To use an
existing cluster, connect before creating the runner:

.. code-block:: python

    import ray
    ray.init(address="auto")

Per-stage actors are named ``<pipeline id>:<stage index>:<description>``, so
the stages are easy to find in the Ray dashboard.

For ``min_vram`` claims, the backend probes the memory of the cluster's
GPUs. Pass ``RayBackend(gpu_memory=[...])`` to set it explicitly.

Lower-level use
^^^^^^^^^^^^^^^

The Ray backend can also run plain streaming graphs, without a protocol:

.. code-block:: python

    from scipion_bridge.backend.ray import RayBackend
    from scipion_bridge.core.streaming import Pipeline

    with Pipeline.from_sink(sink, backend=RayBackend(queue_size=4)) as pipeline:
        pipeline.send(particles=batch)

PyWorkflow (Scipion 3)
----------------------

``convert_protocol_to_scipion3_protocol`` generates a native Scipion 3
protocol class from a Scipion Bridge protocol. Declare it in a Scipion plugin's
``protocols`` module:

.. code-block:: python

    from scipion_bridge.backend.pyworkflow import convert_protocol_to_scipion3_protocol
    from .protocol_model_inference import FoundationModelInference

    FoundationModelInference = convert_protocol_to_scipion3_protocol(
        FoundationModelInference(),
        label="embed parts",
        conda_env="foundation-models",
    )

The generated class:

* **builds the GUI form** from the declarations. Inputs go to an *Input*
  section, as pointers to the matching Scipion objects. Fields go to a
  *Parameters* section as ``IntParam``, ``FloatParam``, ``BooleanParam``,
  ``StringParam`` or ``EnumParam``. Labels and help texts come from the
  ``Field`` declarations.
* **converts data** between Scipion objects (for example ``SetOfParticles``)
  and the array types through type resolution.
* **runs shell commands** through the protocol's ``runJob``. Domains declared
  with ``isolated=True`` run in the given ``conda_env``.
* **allocates temporary files** in the protocol's ``tmp`` directory.
* keeps the original ``__name__`` and ``__module__``, so Scipion's plugin
  discovery lists it.

Install the ``pyworkflow`` extra into the Scipion environment (see
:doc:`../getting_started/installation`).

Choosing chunk sizes
^^^^^^^^^^^^^^^^^^^^

Every batch handed to an external program is written to temporary files, so
the per-batch cost includes this I/O. Under the pyworkflow backend, prefer
large chunks, for example 10,000 particles. With the Ray backend, protocols
that work on in-memory data can use smaller chunks, sized for the GPU.
